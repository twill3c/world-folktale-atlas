# L-DL15 — 和訳が 100% になった土台での数え直し(2026-09-28)

## なぜやったか

別セッションが 2026-09-26 に和訳を **1,225/1,225 話(32 文化圏すべて)**にした。
和訳を材料にしている測定は、すべて 1,113 話のときの数字のままである。

L-DL14 でも同じ取りこぼしをした(本を 3 冊足したのに下流を 2 つ数え直していなかった)。
**二度続けたので、今回は一覧を作り、機械に数えさせることにした。**

## 数え直している途中で見つけた壊れもの(HC-323)

`diagnose_align.py` が `IndexError` で落ちた。追うと、段落対のキャッシュが**壊れていた**。

| 文化圏 | いまの対 | キャッシュ |
|---|---|---|
| ノルウェー | 2,457 | **33** |
| ロシア | 1,934 | **20** |
| ドイツ語圏 | 1,282 | **9** |
| ジャマイカ | 783 | **7** |
| 新しい 3 文化圏 | 1,644 | **無し** |

原因は単純である。`load_region(region, expect=None)` に**古さを検出する引数があるのに、
呼び出し側 3 箇所のどれも渡していなかった**。
作り直す側(`embed_pairs`)は対の数が違えば作り直すよう直してあったのに、
**読む側だけが素通りできた**。

- **任意にした安全確認は、渡されなければ無いのと同じである**
- `align_eval.py` は**落ちずに完走する**。落ちたのは別の経路だった。
  つまりこの壊れ方は、黙って間違った数を出す
- H-09/H-10(写像の学習)の公開済みの数字は、この混ざったキャッシュから出ていた

直したこと: `expect` を**必須**にし、呼び出し側から現在の対の数を渡す。
段落対を埋め込み直し(26,965 対・33 分)、写像を作り直してから H-09/H-10 を測り直した。

### 直したら、二つの結論がひっくり返った

学習に使える対が 10,939 → **18,435** に増えた。

| 分ける対象 | 壊れた材料(09-18) | 直した材料(09-28) | 判定 |
|---|---|---|---|
| H-10a 材料の質(相互最近傍率) | 0.892 | 0.784 | ✓ のまま |
| H-10b 目的の不一致 | +0.031 | +0.041 | ✗ のまま |
| **H-10c 容量(2 層の非線形)** | +0.017 | **+0.076** | **✗ → ✓** |
| H-10d 目的に合わせた学習 | ±0.000 | −0.015 | ✗ のまま |

1. **「e5 本体の微調整(Colab)には進まない」を取り下げた。** 進む条件は H-10c の成立だけと
   登録してあり、直した材料ではそれが成立する。**帯は動かしていない。動いたのは材料である**
2. **「上限に当たっていて学習の余地が小さい」も取り下げた。** 段落対の当たりは 0.934 ではなく
   0.853 で、非線形は段落 → 話を 0.818 → 0.894 に上げている
3. 残った誤りの「1 位が同じ本の別の話」も 36.4% → **8.3%**。
   「誤りの正体は同じ本の似た書き出しだ」という読みも、壊れた材料の上での読みだった

**線形の写像(回転・リッジ)を採らない結論は変わらない**(利得 +0.015 / −0.046、帯 0.05)。
Colab で微調整に進むかどうかは、手元の機では回せないので**別に決める**。

## 仕組み — 古い測定が黙って残らないこと(G-23・新設)

覚えておくことを規律にしない。**材料より古い成果物を機械に数えさせる。**

- `ml/freshness.py` が、コーパス・和訳・問いの集合の最終更新と、
  分析の成果物 **21 個**の最終更新を git から取って比べる
- 古いものは `docs/STALE.md` に**理由つきで**載せ、`/gates/` の
  「測り直していない測定」に名前・測定日・何より古いか・理由を出す
- **台帳に無い古さがあれば検査が落ちる**(`tests/test_freshness.py` 7 件)

**古いこと自体は禁じていない。黙って古いことを禁じている。**
測り直しに数時間かかるものを消すのも、古い数字を新しい顔で出すのも、どちらもしたくない。

新設したその回に **6 個が古い**と出た。5 個は測り直し、1 個(NLI)は理由を書いて開示した。

## 教訓

1. **安全確認を任意引数にしない。** 呼び出し側が渡さなければ、無いのと同じである。
   今回はそれが原因で、**十日間、公開していた判定が二つ間違っていた**
2. **作り直す側を直したら、読む側も同じ回で直す。** 片側だけだと古い材料が黙って読まれ続ける
3. **落ちない壊れ方がいちばん危ない。** 今回は別の経路が `IndexError` で落ちて偶然露見した
4. **判定も数と同じく散文に焼き込まない。** データから引く
