## 2. 検査が正しい訳を却下した(VERIF-FALSE)★

T-JA-06(数の保存)が、**正しい訳を落とした**。

```
✗ GB-9368-024  T-JA-06 第 20 段落で算用数字がすべて消えた ['1914', '1918']
```

原文の `In the World War of 1914-1918` を「一九一四年から一九一八年の世界大戦」と訳した。
**数は消えていない。位取りの漢数字で書いただけである。**
日本語としてはむしろこちらが自然で、検査のほうが日本語を読めていなかった。

直し方: 訳文の漢数字を算用数字に直してから照合する。
`〇一二三四五六七八九` の一対一の置換で足りる(『三十六』のような命数法は扱わない。
ここでの目的は**数が消えていないか**を見ることであって、値を求めることではない)。

> **検査が落ちたときは、まず検査を疑う。** ここでは実装ではなく検査が誤っていた。
> 検査を信じて訳を書き換えていたら、日本語として不自然な訳が残っていた。

## 3. 出荷の成否を、道具の終了コードで判定しかけた(HC-256)★

`vercel deploy --prod` が `Upload aborted` で**二度**失敗した。
失敗として記録し、再試行しようとした。

ところが本番の `index.json` を引いてみると、**和訳の件数はすでに新しい値になっていた。**
その直前の `git push` が Git 連携の自動ビルドを起こし、配布はとうに終わっていたのである。
失敗したのは、**二重にやろうとした二本目**だけだった。

終了コードだけを見ていたら、**成功している出荷を失敗と報告する**ところだった。
さらに再試行を重ねれば、走っている正規のビルドと競合しかねない。

対策:

- `README.md` に「**`git push` で自動デプロイされる。`vercel deploy` は不要**」と明記した
- 出荷の確認は `harness/live.mjs`(公開 URL を実ブラウザで開く)と、
  公開 `index.json` から**その回で変わるはずの値**を引くことで行う

> HC-239 で「偽の失敗は安全側の誤りではない」と書いた。これはその配布版である。

## 4. 進め方(次のセッションへ)

短い話から埋めると、少ない語数で多くの文化圏に届く。実測:

| 選び方 | 話数 | 英語語数 |
|---|---|---|
| 各文化圏の短い 1 話ずつ | 22 | 17,726 |
| 各文化圏の短い 3 話ずつ | 66 | 65,074 |
| 各文化圏の短い 5 話ずつ | 110 | 124,749 |
| 全話 | 709 | 1,201,572 |

次は **各文化圏 5 話ずつ(110 話・15.5%)** が手ごろな刻みである。
そのあとは、収録数の多い本(ドイツ語圏 126・ノルウェー 58・朝鮮半島 53)を
まとめて進めるほうが、割合は速く伸びる。

取り込みの手順は変わらない。

```bash
# data/translations/incoming/batch-NNNN.json に {"STORY_ID": ["段落1", ...]} を書く
.venv/Scripts/python etl/build_translations.py
.venv/Scripts/python etl/export_web.py
git add -A && git commit && git push     # push で自動デプロイ
node harness/live.mjs                    # 本番に対する検品
```
